Leaving Chroma Cloud: to Chroma 1.5.9, single node

Disclaimer. These guides and the scripts they link are provided as is, without warranty of any kind, as stated in the Apache License 2.0. They describe what we measured on 25 October 2026: your data, versions and setup may behave differently. Back up your data and test the migration on a copy first. You are responsible for your data and for every migration you run.

Not sure about your case? Open an issue in the VecturaDB repository, describe your data and your setup, and we will take a look on a best-effort basis.

Chroma 1.5.9 is the open-source Chroma server. It runs as one container, or inside a Python application. It keeps dense search, metadata filters and document filters. It has no sparse vectors, no BM25, no Search API and no collection fork.

VecturaDB, which wrote this guide, is not affiliated with Chroma. We ran every command below on 25 October 2026, against Chroma Cloud and against chromadb/chroma:1.5.9.

1. Start Chroma

docker network create chroma-net
docker run -d --name chroma --network chroma-net -p 8000:8000 -v ./chroma-data:/data chromadb/chroma:1.5.9

The image keeps its data in /data.

2. Copy the data

The chroma CLI is inside the same image. It needs your Chroma Cloud API key and the name of your database.

export CHROMA_API_KEY=<your Chroma Cloud API key>
docker run --rm --network chroma-net -e CHROMA_API_KEY --entrypoint bash chromadb/chroma:1.5.9 -c \
  'chroma login --api-key "$CHROMA_API_KEY" --profile cloud &&
   chroma copy --from-cloud --to-local --host http://chroma:8000 --db <database> --collections <name> --collections <name>'

Repeat --collections once per collection. Two things the CLI does not tell you clearly:

  • --all does not work against Chroma Cloud with this CLI. It asks for 10000 collections in one call, and Chroma Cloud answers 422 Quota exceeded. Our script list_for_copy.py prints the --collections options for every collection of a database.
  • The CLI exits with code 0 even when the copy fails. Read its output: each collection ends with Copy Completed! or with an error.

What arrives: every record, with its document, metadata, embedding and URI, and the metadata of the collection. The settings of the dense index do not arrive: Chroma Cloud uses SPANN, Chroma 1.5.9 uses HNSW with its default settings.

Collections the CLI cannot copy

Two kinds of collections fail:

  • collections with a sparse vector index or a BM25 index: Sparse vector indexing is not enabled in local;
  • collections created with the old hnsw:* settings in their metadata: Cannot set both collection config and schema simultaneously.

A collection that fails stops the copy. Copy those collections with our script copy_without_sparse.py instead:

curl -O https://raw.githubusercontent.com/VecturaDB/VecturaDB/eeec42dbacd6ab2d4efec2b6a899dac25f0846d0/migration/leaving-chroma-cloud/copy_without_sparse.py
pip install chromadb==1.5.9
export CHROMA_API_KEY=<key> CHROMA_TENANT=<tenant> CHROMA_DATABASE=<database>
python copy_without_sparse.py 127.0.0.1 8000 <name> <name>

It copies the records, documents, metadata, embeddings and URIs into a collection with the same name, metadata and distance. Chroma 1.5.9 cannot store sparse vectors at all, not even as plain metadata. So the script writes them to <name>.sparse.jsonl, one line per record, and they are not lost.

On Chroma 1.5.9 those collections lose their sparse and BM25 search. Dense search, filters and the documents stay.

3. Switch the client

Only the line that creates the client changes. The collections are in the default tenant and database of the server.

The examples use 127.0.0.1. With Docker Desktop on Windows, localhost went to the IPv6 port of the container, which closed the connection; 127.0.0.1 worked everywhere.

Python (chromadb 1.5.9):

import chromadb

# Before:
# client = chromadb.CloudClient(api_key="...", tenant="...", database="...")
client = chromadb.HttpClient(host="127.0.0.1", port=8000)

JavaScript (chromadb 3.5.0 on npm):

import { ChromaClient } from "chromadb";

// Before:
// const client = new CloudClient({ apiKey: "...", tenant: "...", database: "..." });
const client = new ChromaClient({ host: "127.0.0.1", port: 8000, ssl: false });

.NET (ChromaDotNet.Client 2.18.0):

using ChromaDB.Client;

// Before:
// var options = ChromaConfigurationOptions.FromConnectionString("Endpoint=https://api.trychroma.com;Token=...;Tenant=...;Database=...");
var options = ChromaConfigurationOptions.FromConnectionString("Endpoint=http://127.0.0.1:8000");
using var http = new HttpClient();
var client = new ChromaClient(options, http);

With each of the three clients, the same query on the same copied collection gave the same records on Chroma Cloud and on Chroma 1.5.9.

Chroma 1.5.9 has no API keys: the server accepts every request. Keep it on a private network, or behind a proxy that checks a key.

4. Hosted embedding models

chroma-cloud-qwen and chroma-cloud-splade run on Chroma Cloud and stop with it. See Hosted embedding models: the same open models, run locally, gave the same search results in our tests.

On Chroma 1.5.9 only the dense model matters: SPLADE vectors are sparse, and Chroma 1.5.9 cannot search them.

5. Check

verify.py compares each collection on both sides: count, ids, documents, metadata, URIs, embeddings, and the distances of three dense queries.

curl -O https://raw.githubusercontent.com/VecturaDB/VecturaDB/eeec42dbacd6ab2d4efec2b6a899dac25f0846d0/migration/leaving-chroma-cloud/verify.py
python verify.py 127.0.0.1 8000 <name> <name>

In our run, all records were the same. One difference is worth knowing. HNSW is approximate: in a test collection with 300 identical embeddings, it did not find the two records at distance 0, which Chroma Cloud found. The same happens in VecturaDB. With real data, run verify.py on your largest collections.
