Deploy / VecturaDB / Google Cloud

VecturaDB on a Google Cloud VM

One VecturaDB server in your own Google Cloud project, with its data on a disk of its own, HTTPS, API keys, allowed IP addresses and snapshots. From about 13 USD a month on your Google Cloud bill.

Open in Cloud Shell README of the template

Disclaimer. This template and its scripts are provided as is, without warranty of any kind, as stated in the Apache License 2.0. The numbers on this page are what we measured with VecturaDB 1.0.0-preview.8 on 6 November 2026 in europe-west1: your region, sizes, data and versions may behave differently. You are responsible for your data: back it up, and test a restore on a copy before you rely on it.

Not sure about your case? Open an issue in the VecturaDB repository, describe your data and your setup, and we will take a look on a best-effort basis.

What it creates

The template runs VecturaDB 1.0.0-preview.8 (ghcr.io/vecturadb/vecturadb:1.0.0-preview.8), built from Chroma, with sparse vectors, BM25, hybrid search, collection fork and API keys. The same template can also run Chroma 1.5.9.

VecturaDB keeps the Chroma API: the Chroma clients connect with the url output and the API key. In our tests the Python client (chromadb 1.5.9) worked over HTTPS with the key, and VecturaDB refused the requests without it.

Deploy

Open in Cloud Shell

Google Cloud has no form that creates a deployment from a link. The button opens Cloud Shell, the terminal of the Google Cloud console, with the template of the tag gcp-v1.1.1 and a guide on the side, with VecturaDB already chosen, which runs Terraform step by step.

  1. Google asks to confirm the clone of the repository. Without “Trust repo”, Cloud Shell is temporary: its files are deleted at the end of the session, and it has no credentials until the guide signs you in. If Google asks to authorize Cloud Shell when it opens, it is not needed: click outside it to close it, the guide signs you in. In a temporary Cloud Shell gcloud auth login first says that you are already authenticated: answer Y.
  2. The guide turns on the APIs that the template uses, installs Terraform, and creates a Cloud Storage bucket for the state of Terraform, <project id>-chroma-tfstate, with versioning and without public access.
  3. You give the IP address of your computer and the API key, then terraform apply creates everything. The settings file goes to the bucket too, next to the state; the key goes to Secret Manager only. The key is optional with the allowed IP addresses, and required for public access.

To change a setting or delete the deployment later, open the guide again: it gets the state and the settings back from the bucket.

In our testsTime
Deployment from zero, until the server answered over HTTPS465-532 s
Terraform installed in Cloud Shell, on 5 Novemberabout 40 s

Most of the creation is the first boot of the VM, which installs Docker and Caddy from the package repositories, so its time depends on them.

With Terraform 1.11 or later on your computer:

cd gcp/vm
gcloud services enable compute.googleapis.com iam.googleapis.com secretmanager.googleapis.com storage.googleapis.com
gcloud storage buckets create gs://<bucket> --location=europe-west1 --uniform-bucket-level-access --public-access-prevention
terraform init -backend-config=bucket=<bucket> -backend-config=prefix=vecturadb
export TF_VAR_project_id=<project id> TF_VAR_api_key=<your key>
terraform apply -parallelism=2 -var-file=vecturadb.tfvars -var 'allowed_ip_ranges=["203.0.113.10/32"]'

Give the key again at every apply: an apply without it removes the key. The template and its README are in the VecturaDB.Deploy repository, under gcp/vm.

The commands run Terraform with two operations at a time: in our tests from Cloud Shell, with the default of 10, 5 plans out of 11 failed with a refused connection to the Google APIs, and with 2 none out of 11.

Access and HTTPS

AccessWhat is openAddress
Allowed IP addresses443 from your IP ranges; 80 for the certificate onlyhttps://, with the external IP or your domain
Public443 and 80 from anywhere; only with an API keyhttps://
InternalNothing from the internet; port 8000 inside the VPChttp://, on the private address
  • Caddy gets a Let's Encrypt certificate and forwards to the server on 127.0.0.1.
  • Without a domain, the certificate is for the external IP itself, and Caddy renews it.
  • Port 80 answers only the challenge of the certificate. There is no SSH: the agent of the VM reads its settings from the metadata of the VM.
  • terraform apply ends only when Caddy holds the certificate and the server answers.
  • Every request needs the API key, in the x-chroma-token header. The key goes to Secret Manager as a write-only value: it is not in the state of Terraform, nor in the settings file. The VM writes it to a file readable by root only.

  • We tested only e2-micro.
  • The e2 shared-core types run at a fraction of a vCPU and burst above it for short periods: e2-micro at 0.25 of a vCPU, e2-small at 0.5, e2-medium at 1. A server that is busy all the time needs a larger size.
  • The API key adds the secret: 0.06 USD a month beyond the 6 free secret versions of the billing account, and 0.03 USD per 10,000 accesses beyond the first 10,000. The VM reads the key at every configuration.
  • Not in the table: outbound traffic, the snapshots of the backups and the bucket of the state, a few KB.

Backups and restore

  • With backups on, the default, a snapshot schedule of Compute Engine takes snapshots of the data disk every 24 hours, or every 4, 6, 8 or 12 hours, and keeps them 7 days.
  • The snapshots are billed at 0.05 USD per GB a month in europe-west1, for the data they hold.
  • The snapshots are not part of the deployment: terraform destroy leaves them.
  • The snapshots are taken while the server runs, so a restored disk is like a disk after a power cut: the restore checks its file system before it uses it.
  • A snapshot taken while the server saves the index of a collection can give that collection back broken, as a power cut would. It can happen to a collection of more than 1,000 records, where the server starts saving its index, with Chroma 1.5.9 and with VecturaDB. In our tests of 6 November 2026 it happened twice, each time to a collection of 2,000 records added a few seconds before the backup: on AWS with VecturaDB (“Error creating hnsw segment writer”) and on Container Apps with Chroma 1.5.9 (“Error getting embedding”). So take an on-demand snapshot while nobody writes. The scheduled ones are set at 02:00 UTC: keep the writes away from that hour.

Restore

In the folder of the template, after terraform init with the same bucket and folder:

gcloud compute snapshots list --filter="labels.chroma-backup=vecturadb"
./restore.sh <snapshot name>

restore.sh creates a disk from the snapshot and attaches it to the VM. Then the agent of the VM stops the server, replaces the data with the data of the snapshot, and starts the server again. In the end the script detaches and deletes the disk. The data written after the snapshot is lost: take a snapshot first if you may want it back. The data disk stays the same, so the snapshots go on.

In our testsTime
Snapshot by hand39-43 s
Disk from the snapshot24-26 s
Attach6 s
Copy on the VM, until the server answers8 s
Detach and delete8-9 s

With VecturaDB 1.0.0-preview.8, as with Chroma 1.5.9, after each restore the server held all the collections of the snapshot, also the one written right before it.

Updates

  • To change the server, its image, the access or the key, open the guide again, change the settings and apply: the agent of the VM pulls the image, stops the old container and starts the new one, with the data on the data disk. An apply that changes none of them does not restart the server.
  • The server does not answer during the switch.
  • An apply never replaces the VM, so it never moves the data disk.
  • Docker starts only once the data disk is mounted: a VM that boots without it serves nothing, rather than an empty database.
  • Ubuntu installs its security updates by itself. Caddy comes from its own repository, which they leave out.

In our tests a switch from Chroma 1.5.9 to VecturaDB with an API key took 25 seconds, and VecturaDB read the collections written by Chroma. A new key took 23 seconds, and afterwards the client could no longer connect with the old key.

Delete everything

terraform destroy deletes the VM, the data disk, the network, the IP address, the service account and the secret. The snapshots stay: delete them after the VM, so that no new snapshot comes after the cleanup. Then delete the state and the settings in the bucket. The last step of the guide has the same commands.

terraform destroy -parallelism=2 -var-file=vecturadb.tfvars && for s in $(gcloud compute snapshots list --filter="labels.chroma-backup=vecturadb" --format="value(name)" --verbosity=error); do gcloud compute snapshots delete $s --quiet; done && gcloud storage rm --recursive --all-versions gs://$BUCKET/vecturadb

In our tests terraform destroy took 99-134 seconds from a computer; afterwards nothing of the deployment was left in the project.

Limits

  • One VM and one disk: no high availability.
  • While the VM restarts or an update switches the container, the server does not answer.
  • The snapshots are in the same region.
  • The certificate of an IP address is valid for about 6 days: Caddy renews it while the VM runs.
