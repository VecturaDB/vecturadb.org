Chroma clients, step by step

Each Chroma client we ran against VecturaDB and against Chroma 1.5.9: the result of each step on the two servers, the notes and the defects of the client. The summary, one row for each client, is on the Clients page.

Disclaimer. These results are provided as is, without warranty of any kind, as stated in the Apache License 2.0. They describe what we measured on 29 October 2026: your client, its version and your setup may behave differently.

Not sure about your client? Open an issue in the VecturaDB repository, name the client and its version, and we will take a look on a best-effort basis.

Sparse vectors, BM25, Search and API keys

VecturaDB also has sparse vectors, BM25, the Search API and API keys on the single node, where Chroma 1.5.9 does not have them. We tested them with the two Rust crates, against VecturaDB 1.0.0-preview.3.post1 and against Chroma 1.5.9:

  • Sparse vectors, BM25 and Search, with chroma 0.15.0. On VecturaDB the crate created a collection with a sparse vector index, added 3 records with the BM25 vectors it computes from their documents, and searched them with the Search API: the dense search for [1, 0] gave r1 then r3, and the BM25 search for "apple" gave r1. Chroma 1.5.9 rejected the index with 400 "Sparse vector indexing is not enabled in local".
  • API keys, with both crates. We started both servers with one API key in CHROMA_SERVER_AUTHN_CREDENTIALS. VecturaDB answered 401 "Permission denied." without a key and with a wrong key, and accepted the right one: chroma 0.15.0 sent it with ChromaAuthMethod::cloud_api_key, chromadb 2.3.0 with TokenAuth in the X-Chroma-Token header. With the right key, the other steps gave the same results as without keys. Chroma 1.5.9 has no built-in authentication: it accepted every request, with any key or none. To set up API keys, see API keys.

How we tested

  • The servers: chromadb/chroma:1.5.9 and ghcr.io/vecturadb/vecturadb:1.0.0-preview.3.post1, for linux/amd64, with the default command of the image. The image of VecturaDB was sha256:b7a7fcf464a19ae1987e2ebd02bf68ea1afb25446d274ab083f1a430e0854ff5.
  • A new container for each client and each server, with an empty data folder, on a Docker network: the client reached the server at port 8000. No API keys outside the API key steps, the default tenant and database.
  • Each client ran in a container of its language, with its version pinned.

The steps were the same for every client, with embeddings of two numbers given by hand, so no embedding model was involved:

  1. heartbeat;
  2. pre-flight-checks;
  3. create a collection, with the cosine space;
  4. add 3 records with documents and metadata;
  5. query with [1, 0] for 2 results, expecting r1 then r3;
  6. get by id;
  7. get with the filter {"n": {"$gte": 2}};
  8. delete one record, then count, expecting 2;
  9. delete the collection.

The one difference between the two servers is in step 2: VecturaDB adds its server block to the answer of pre-flight-checks. The clients that show the raw answer, Python, JavaScript, Dart, Ruby and both PHP clients, took it without errors, with the same max_batch_size, 5461.
